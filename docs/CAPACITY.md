# 容量模型与压测（P2）

## 实测：服务层（本机 Docker，compose-prod，3 个 app 副本，scripted 后端）

经 nginx LB → 3 副本 → Redis，用 `bench/loadtest.py`：

| 并发 | 吞吐 | p50 | p95 | 429 | LB 分散（3 副本） |
|---|---|---|---|---|---|
| 50 | **771 req/s** | 63ms | 105ms | 63 | 1010 / 981 / 1009（均匀） |
| 150 | 475 req/s | 303ms | 361ms | 21 | 1281 / 1330 / 1389（均匀） |

**结论（实测，不是推测）**：
- **LB 真分散**：三个容器各处理约 1/3，nginx 负载均衡确实生效。
- **有吞吐甜点**（≈并发 50，~770 rps）；超过后**优雅降级**（延迟升、不雪崩），超载时 429 背压兜底。
- 加副本即横向扩展（LB 分散已证），app 层不是瓶颈。

> 注意：scripted 后端测的是**服务层管线**吞吐（LB/并发/背压/Redis）。真实瓶颈是**模型**，见下。

## 容量模型（生产是「模型受限」）

服务层 ~770 rps 远高于任何单卡模型出词速度，所以**容量由模型机队决定**，不由 app 层：

```
单节点回复速率 ≈ T(tok/s) / R(回复token数)      # T=节点吞吐, R=平均回复长度
集群回复速率   ≈ N × T / R                       # N=模型节点数
要达目标 Q(req/s)：N = ceil(Q × R / T)
```
- **app/LB/Redis 层线性扩**（LB 分散已实测），不是约束。
- **模型节点扩**：`pool` 后端 + `join_cluster.sh` 自注册（已实测轮询/故障转移），加一台即加 `T/R`。
- HPA 按 CPU/并发自动扩 app 副本（`deploy/k8s` 已配）。

## 仍需真环境标定（诚实）
- **T（单节点模型吞吐）要在真 GPU/Mac 上基准**——本机单 `mlx_lm.server` 量级 ~几十 tok/s，
  但生产用 **vLLM 连续批处理**时，一张卡能并发服务很多请求，T 会高出一个量级，容量公式里的
  T 必须按目标硬件实测。
- vLLM 后端**无需新代码**（OpenAI 兼容）：`ARK_BACKEND=api`、`ARK_API_BASE_URL=http://<vllm>/v1` 即可。
